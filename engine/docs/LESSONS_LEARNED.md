# 实测经验总结

## 本轮发现

1. 环境依赖要落到项目 `.venv` 中，避免全局 Python 缺 OpenCV、Jinja2、Rich 时无法跑真实视频。
2. Windows 下 FFmpeg/ffprobe 输出可能包含非 GBK 字符，子进程读取必须使用 UTF-8 且 `errors="replace"`。
3. OpenCV `cv2.imread` 对中文路径不稳定，关键帧读取必须使用 `np.fromfile + cv2.imdecode`。
4. HTML 报告不能直接输出 Python 字典，关键指标必须转换为中文标签和清楚的数值格式。
5. 小红书等平台链接可通过 `yt-dlp` 成功下载，但这类能力依赖平台当前策略；失败时应提示用户提供本地视频。
6. fast 与 deep 给出的结论差异较大，deep 更容易发现重复帧、静止段和低清比例问题，因此项目取消快检。
7. 多视频评分最方便的入口不是多次单独 `review`，而是一次 `batch` 接收多个链接、文件和文件夹。
8. 批量总览只能做导航和摘要；每个视频仍需要独立完整 HTML/JSON 报告，方便逐条复盘。
9. 时间轴 marker 上放长文本会产生叠字，marker 只保留点位和 hover title，说明文字放到独立事件卡。
10. Top 问题列表和关键帧证据区必须是响应式多列布局，浏览器宽度变化时自动从 1 列到约 5 列。
11. 证据图片不能用裁切式展示；横屏、竖屏都应 `object-fit: contain`，保证主体完整。
12. 结论区要比普通内容更醒目，`最终建议` 应放在总评分下方、分项评分前方，`是否可发布` 是主结论。
13. Codex/工具脚本在中文项目上应使用 UTF-8 容错读取子进程输出，避免 Windows 默认 GBK 解码失败。

## 已做修改

- `postscore review` 默认并固定使用 `deep`。
- 移除 `fast` 可选值；`--mode fast` 会被 CLI 拒绝。
- 默认深度抽帧仍以 3 fps 为目标，但最多约 360 张关键帧。
- 默认关键帧宽度上限为 720 像素，以减少 OpenCV 计算耗时。
- 报告关键帧指标统一中文化。
- 新增/固化 `batch` 批量评分：多源输入、文件夹扫描、失败不中断、总览 HTML、CSV 和每条视频完整报告。
- 报告时间轴改为 marker + 独立事件卡，解决叠字。
- Top 问题和关键帧证据区改为自适应网格。
- 证据图改为完整展示，不裁切横屏或竖屏主体。
- 最终建议移到总评分下方，并用醒目结论区展示。
- 项目 skill、AGENTS 使用规则和 README 已同步批量评分及报告验收规范。
- `repo-router` 工具脚本已修复中文仓库输出解码问题。

## 40 秒目标

40 秒可以作为 3 分钟左右视频的默认性能目标，但不是硬保证。影响因素包括：

- 视频是否需要先下载。
- 视频编码是否容易解码。
- CPU 和磁盘速度。
- 是否手动提高 `--sample-fps`。
- 是否设置 `--max-sampled-frames 0` 取消上限。

默认策略会优先保证稳定深度检测，同时把 3 分钟视频的抽帧量控制在约 360 张以内。
